# The concept

## Problem

One has a function that is to go on the network — something other people or their agents should be able to use. The author faced exactly this case: drafts were to be filed into mailboxes over IMAP, invoked from outside. For something like that one does not build an enterprise service but a small program — and one wants to have it in operation before the appetite fades.

Then come the questions that arrive within a few days for every service, however small: How does one create an access? Who may use it, and for what exactly? How does one check whether the configuration is right *before* restarting? How does one see what is pending? How does one clean up? And how does TLS get in front of it?

The reflex says: another tool. A little admin script that writes into the same store. A web UI for administration. A debug endpoint, "internal only". A second, slim image for maintenance tasks. Each of these things looks sensible on its own, and together they turn the small service into a project — for each is a second implementation of the same knowledge: it has to know the configuration format, the storage layout, the validation rules, the version. From then on two things age side by side, and at some point the tool from version 1.2 writes something that the service from version 1.5 reads differently.

The second reflex is quieter and more expensive: another function. If the service is running anyway, it can surely solve the neighboring problem at the same time. From that moment on there are callers who are to be allowed one thing and not the other — and with them permissions, roles, an administration for them and someone to run it. The service that began as an afternoon project now has a permission concept.

Three roles carry the problem, and in a small service the first two often coincide in one person — that is the normal case this dossier is written for. **The builder** writes both and notices the duplication first at the third configuration field that has to be carried over in two places. **The operator** has to ship two delivery artifacts, keep two versions in view and, in a fault, know which of the two is currently right. **The successor** finds, months later, a tool whose relation to the service nobody can explain any more — and does not dare to use it.

The usual way out — discipline, shared libraries, a monorepo — mitigates the duplication but does not abolish it: two delivery artifacts remain two delivery artifacts, and they are built separately, shipped separately and forgotten separately. The structural answer starts one level deeper: what does not exist separately cannot age separately — and what is not ambiguous in the first place needs no permission management.

This dossier is therefore not a doctrine of architecture but a **foundation for starting to build**: a procedure in eleven steps (below) and thirteen rules that carry it (the `rules/` directory) — both are adopted before the first line is written. Whoever begins this way has already made the decisions one otherwise makes one by one and mostly under time pressure — and is spared exactly the by-products that make the small service big.

## The concept

Everything begins with the function: **a service carries exactly one.** It is its purpose, describable in one sentence — "put a mail into an IMAP folder". The network surface splits it into methods: a main method and the **helper methods** without which it does not work. In the example, the file upload is not a second function but the preparation step for attachments; added to it are the status enquiry about the submission and the cleaning up of what was uploaded. All methods serve the same function and share the same access — there is nothing that one caller would be allowed to do and another not.

From this follows the construction form: **one artifact with several modes.** The same executable program runs as a service and executes the commands — check, show state, configure, issue an access, clean up; which mode applies is decided by the invocation. If the service needs further process kinds — a worker for a queue, say — that too is a mode and not a second program. What is shipped is **one delivery artifact**: an image or a binary, against which the commands run as well, in the same environment, with the same version. Both modes read **the same configuration** with the same code, and the check command passes exactly the judgment that the start would pass; how the configuration is found, judged and supplied with secrets is said by two imported concepts, `one-configuration-one-judgment` and `where-a-secret-comes-from`. Whatever must survive a restart lies **outside** the artifact, at named places.

The core of the cut, however, sits in what the commands do: **they configure the function for the specific use case and create the access for exactly that configuration.** The service can "put a mail into an IMAP folder"; the command determines into *which* mailbox and into *which* folder — and in the same motion issues the access artifact that embodies exactly this variant. The caller never chooses what the configuration has determined; they invoke the function, and where it takes effect is not in their request.

That is the reason the rest turns out so small. There is no moment at which someone *gives* rights to an existing access — the granting is the configuration, and the access is its handle. So this service needs **no permission model, no roles and no administrator**: administration is configuration, and whoever may change the configuration file administers. Accordingly, the **running service has no management surface** — no management path, no debug route — and the **permission cut runs between the modes**: the service mode works with the narrowest permissions sufficient to run; writing happens only in command mode, enforced through users and file permissions.

The principle is not new; it stands in the ancestry of the twelve-factor rule that admin processes run in an environment identical to the service's and that their code must ship with the application code (see the sources). What is new is the consistency with which a cut is made of it here: not "admin code lies with the application code" but "admin code *is* the application code, in a different mode" — and the connection with the one function, which dissolves the permission topic from the outset. For whoever wants to put a function on the network, that is the whole effort: one program with a few more commands, one delivery artifact, one configuration file, one directory beside it, one proxy in front.

**Load-bearing structure.** F1 carries everything: with a second independent function, permission distinction, roles and administration return, and F9 as well as F10 lose their ground. F2 carries the tooling part; without "one artifact", F4 (one delivery artifact) and F5 (one judgment) are not enforceable but mere intentions, and F3 would have no place. F6 is the condition for F4 being worth anything in operation — an artifact that drags its state along is not interchangeable. F7 and F8 are the security separation that this cut makes possible in the first place: without a command mode, administration would have to go somewhere, and the only remaining place would be the network surface. F9 and F10 hang together — if F9 falls, the intermediate state arises in which administrative rights are needed, and F10 falls with it. F11 carries independently and holds also for services that adopt nothing else from this concept. F12 draws the line that F6 and F8 presuppose: without it the variants slip back into the configuration file, and the permission cut has no object. F13 is independent like F11; it keeps the one deliverable of F4 deployable without a hand at the target.

## The procedure

The rules say what must hold. This section says in which order one proceeds and what is on the table at the end of each step — that is the actual utility for whoever wants to get going. Steps 0 to 3 are half an hour of thinking and decide everything that follows; whoever skips them makes up for them later under worse conditions.

**0 · Check whether it must be a service at all.** Whoever invokes the function either sits on the same machine or somewhere else. If they sit there — a script, a scheduler, an agent on the same machine — then the answer is a command-line tool and not a service: the access control is provided by the permissions of the operating system, and network surface, access artifacts and proxy fall away entirely. Only when the caller comes over the network, or is to come later, does the rest of this procedure pay off. *Result:* a reasoned decision. If it falls against the service, steps 1 to 3 are still useful and the rest is unnecessary.

**1 · Write the sentence.** One sentence that says what the service does — with no "and also". If it will not come out, the cut is not found yet, and everything else would be premature. *Result:* the sentence. It later becomes the short description of the service, the first line of its command help, and the entry under which someone finds it again. (F1)

**2 · Derive the methods.** From the sentence follows the main method; added to it are the helper methods without which it does not work — preparation (an upload, say), status enquiry about the submission, cleaning up what was prepared. *Result:* the method list. Whatever will not subordinate itself here does not belong in this service: it is struck, or it becomes a second service. (F1)

**3 · Determine the variant.** What differs from one use case to the next — target system, storage location, limits? This question is the pivot of the whole cut: its answer is exactly what the configuration entry later carries, what the access embodies, and what the caller consequently never chooses. *Result:* the field list of the variant. (F9)

**4 · Define the configuration.** One file with the global settings; the variants from step 3 are not configuration but store (F12), created later by the setup command. Secrets are not in the file but referenced from it. Precedence, the empty value and showing the source follow `one-configuration-one-judgment`, the origin of start secrets `where-a-secret-comes-from`; their choices are decided here with the user. *Result:* configuration schema and the recorded decisions. (F5)

**5 · Name the state locations.** What must survive a restart — the store of variants and accesses, data, queues, uploads? Each gets a named place outside the artifact, configuration and state apart, operating data sensibly separated per variant. *Result:* the directory layout. (F6, F12)

**6 · Set up the command tree — before the domain logic.** At minimum: start the service · check the configuration (optionally with a connection test against the target system) · show state · set up, change and remove a variant · version. Setting up a variant also issues the access — one command, not two (F9); there is deliberately no separate "issue access" command, but there is one for renewing an existing access. Add the exit codes and the machine-readable output. This is also where it is decided whether commands are only started locally or additionally enter the system over another channel (W1); both with the user. The order is deliberate: with the command skeleton finished, everything else can be checked through commands instead of having to be tested through the network surface. *Result:* the runnable skeleton that can do nothing yet but explain itself. (F2, F3, F9)

**7 · Build the service mode.** The network surface offers exactly the methods from step 2; the access check looks up in the store what the presented access embodies; there is no management path and at most a readiness point that says nothing but "running". If the service mode finds a store of an older structure at start, it migrates it before it listens (F13). *Result:* the service, runnable against a hand-written configuration. (F1, F7, F13)

**8 · Finish the setup command.** The command created in step 6 now gets its effect: it configures a variant and in the same motion creates the access for it — show the access artifact exactly once, keep only its hash and a harmless short identifier, renewal as its own command. *Result:* the path from "the service runs" to "someone may use it" — without a secret being left lying anywhere. (F9)

**9 · Package and set up the delivery.** Build one delivery artifact whose entry point is the service mode and against which the commands run in the same environment; this is where the form of the artifact is fixed, binary, package or directory (F2). More is decided here than it looks — and whoever builds the service *for someone*, as an agent for their user, say, **asks explicitly at this point instead of choosing**: Should a container image be provided, or does the package or the binary suffice for the target environment? Should the build pipeline be set up along with it, so that the image is built and published automatically for every version? And should the deployment file then point at that published image — which also settles whether the target machine can reach the registry and, for a non-public source, with which credentials. The three questions cost a minute and are expensive later: switching from "builds locally" to "pulls the published image" touches every deployment site once more. *Result:* the artifact and a delivery directory — container description, deployment file, example for the reverse proxy, unit for the process form and, if wanted, the build pipeline. (F2, F4)

**10 · Establish the operating form.** Local endpoint, reverse proxy in front with the public name and the certificate; separate users and file permissions, so that the service process reads where the commands write. *Result:* the service is reachable, and the permission cut sits in the process form instead of in good intentions. (F8, F11)

What this procedure deliberately does not prescribe: language, framework, data storage, interface dialect. It fixes the order and the results, not the means.

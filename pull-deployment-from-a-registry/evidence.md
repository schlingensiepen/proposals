# Evidence

This section separates what has been built and operated, what remained open in it, and what serves as illustration. The evidence is the delivery of the author's mail-filing service — a service that accepts files and mail jobs over HTTP and files the messages built from them into a mailbox folder over IMAP, built as one artifact with several modes and delivered as an image from a registry, in operation under a public name since September 2026. Every incident in the problem and in the rules comes from this delivery; its repository is not publicly accessible. **Nothing in this section claims as built what the writer has not seen in the build pipeline, in the container description or in the deployment files**; what was not seen stands as not met or as not measured.

## Case 1 — Reference implementation: the build pipeline and the deployment files of the mail-filing service

**What it is.** The delivery consists of a container description, a build pipeline for a build service, and a delivery directory with three deployment files, a proxy configuration and a process unit for operation on the host. The build pipeline has existed since August 2026 and became what this concept describes in September 2026, within a single working day and in three consecutive steps; the incidents in between are the origin of F2 to F7.

**Built and seen in the build pipeline.** *(F2)* The build pipeline first builds the image into the local runtime of the build environment, starts it with a freshly created state location and a throwaway password, and waits up to two minutes for the image's own health check to report "healthy" — not for a port; if it reports "unhealthy", the run aborts at once and prints the container's log. After that it requires seven addresses on both ports to answer with 200, among them the self-description without access; the administration secret generated on first start to appear exactly once in the log; that secret to be accepted and an invented one refused; after a restart of the container, the same secret to still work and not to have been written to the log a second time; and the version information of the running service to name exactly the source revision that was passed in as a build argument. Only then follows the step that publishes. The container description carries the health check, a user with a fixed ID who owns the state location, and the build stamp as an environment variable with the default "unknown". *(F3)* Since this rebuild the names are computed by a tool that sanitizes the branch name, takes over a version tag and produces one name per build from the full source revision; the build pipeline says in a comment why: a branch with a slash in its name had yielded "invalid reference format" and no image. *(F4)* The same tool writes `latest` only when the build runs on the default branch; that too is in the comment with its reason. *(F5)* The build pipeline carries in its header the sentence that the image's visibility is a setting of the registry of its own, not the repository's, and was set separately; the proxy-less deployment file says that no login is needed, that the anonymous fetch was checked, and that a fork of the repository that makes itself public has not thereby published its images. Measured at the state of this concept, during its review: an anonymous fetch of the manifest gets through; the image can be pulled publicly. About the visibility of the repository this concept says nothing — it is not the subject of the measurement, and F5 forbids inferring it from a setting or a memory. *(F6)* Two of the three deployment files name a published image from the registry. The header of the file for the server in the trusted network states: that it is deliberately without proxy and without TLS and what that costs (administration secret, every access and the mailbox password in clear text; the administration port does not belong on the open network); the three steps in order — pull, start, read the secret from the log; that no login to the registry is needed; which ports apply inside and how to change the outer ones; that the administration secret stays empty so that the service generates one, and that a variable is passed through instead of being defined empty; and where the state lives and that it outlives the container. The file for the acceptance run on the author's own machine states its price as well and says how to switch from "names the image" to "builds locally". *(F7)* The build pipeline requires the version information of the running instance against the built state (see F2); the container description says why: the package version does not move between two changes, and without the stamp an operator cannot answer the question "what is running here?".

**Incidents, stripped down.** *(F3, F4)* The first build pipeline formed two names by hand: `latest` and the branch name, for every build. On the first build on a branch whose name carried a slash, the build step succeeded, publishing failed on the name, and no image came into being. Two things are seen: the triggers of the build pipeline have been, since its first state, the default branch, version tags and the manual start; and the name in the deployment files can only come from a build of the working branch. The conclusion from this — inferred, not seen — is that this build was triggered by hand; and exactly such a build would have overwritten `latest` under the old rule. Both were replaced by the computation in the first step of the rebuild. *(F2)* The smoke test was the second step, with the reason given in the build pipeline that a successful build only says that the package installs, and nothing about entry point, permissions and health check; the third step passed the build stamp into the image and required it back in the smoke test. *(F7)* Twice in a row, on two consecutive rollouts: after a build and a rollout the version information kept naming the old state; the name had stayed the same, the runtime had taken the image from its local cache. The version information had come into being only shortly before, after a container had run for days seven changes behind the state being discussed, without anyone being able to see it. *(F5)* In the same move: the repository had been made public, the image had not; a fetch failed with "unauthorized", the fault-finding went to the credentials. Afterwards the visibility was set, checked anonymously, and the login was struck from the deployment file. *(F8)* Some days after the rebuild, external callers failed with a generic connection error while every client checked by hand got through. The measurement showed: the reverse proxy in front advertised a further protocol on a UDP port through `Alt-Svc`; a client that speaks the protocol ran into a timeout; the UDP port answered nothing; the advertisement was valid for thirty days. A checking agent had earlier offered "the server blocks cloud addresses" as the explanation.

**Not met, and named as such.** *(F6)* The **reference deployment file** — the one with a proxy in front, TLS and two names, which is in operation — **builds the image locally**. Its comment says this is so as long as the repository is private. Whether the repository is private today, this concept does not say — its visibility is not measured. Measured is only that the image can be pulled anonymously (above, F5); the file could therefore name it, however the repository stands, and the comment binds the local build to a condition that no longer matters for the image. The exception is named; that the file in operation is the exception and not the rule remains the shortfall. *(F3, F6)* The two deployment files that name a published image name it through the **sanitized name of a working branch** — a moving name that is, moreover, not the default branch. No deployment file names an immutable name, and none says what kind its name is or how to switch. There is no version tag: at the state of this concept the source carries not a single version marker, so no image with a version name exists either, although the build pipeline would produce one. *(F4)* The most instructive case, because it occurred **and** was fixed between the review and the publication of this concept. During the review it was measured: `latest` and the name of the default branch pointed in the registry to **the same digest**, and it came from the **very first build** — before the build stamp and before the administration surface that can be switched off. The default branch lay more than ninety changes behind the working branch, its last change dating from before the implementation. The rule was kept, and the promise was still not met: whoever pulled without a name got, literally, the first build. It was fixed by merging the working branch into the default branch — and **not** by changing anything about the rule. A new measurement after the build shows `latest` and the default-branch name on the digest of the new image. That is the point of F4 in one sentence: the mechanism was right the whole time; what it pointed to was wrong. A promise bound to a source is only as good as the upkeep of that source — and that is an action of the operator, not of the build pipeline. *(F5)* The visibility measurement is **not a step of the build pipeline**; it was done by hand, and the deployment file asserts its result in a comment. A step without the build credential that fetches the manifest anonymously does not exist. *(F7)* The check after the rollout is **a practice of the author and stands in no shipped file**: the header of the proxy-less deployment file names pull, start, read the log — not the call that reports the state, and not what to compare it with. The information itself exists only through the administration surface on the network, behind the administration secret; the artifact's version command prints name and package version and **not the build stamp** — for the operator without the administration secret and without a shell there is thus no way to the question F7 asks. *(F2)* The reference does **not** have the assertion "the state lies outside the container": it restarts the same container and removes it only during cleanup. Any state survives a restart of the process, including state in the writable area of the container itself; what the step shows is the narrower point — that the administration secret generated on first start still works and is not logged a second time. The first draft of this concept had credited the restart with the wider claim; the finding came from the review, and F2 has since carried recreation as an assertion of its own. Furthermore the build pipeline **builds twice**: once into the local runtime for the smoke test, once with publishing, from the same source with the same arguments. That both are the same image is guaranteed by the build environment's cache, not by a digest carried from the tested to the published image (not yet settled). And the smoke test checks the write permissions of the user inside the container against a freshly created named state location that the runtime creates itself — not against a host directory passed in, where permission problems arise in practice. *(F8)* **Open.** The shipped proxy configuration contains no line that switches off the advertisement of the third protocol; the measurement has been reported to operations, no change has been made, and a check with a client that follows the advertisement belongs to no step of the delivery.

**State of play, honestly.** Built and in operation are the smoke test with its list including restart and build stamp, but without recreation of the container (F2); the computed names with one immutable name per build (F3); the restriction of `latest` to the default branch (F4); the measured visibility as an action and as a sentence in the deployment file (F5); two deployment files that name a published image and state in their header price, steps, login, ports, variables and state location (F6 for the most part); and the build stamp that the smoke test requires (F7 in its precondition). Met between review and publication was the promise of `latest` — not through a change to the rule, but by bringing the default branch up to date (F4, above). Not met are: the reference deployment file that builds locally (F6); moving working-branch names in the other two and no immutable name in any of them (F3, F6); the visibility measurement as a step of the build pipeline (F5); the check call after the rollout in the deployment file and in the artifact's version command (F7); recreation of the container in the smoke test and carrying the digest from test to publishing (F2); and F8 as a whole — the finding is measured, not fixed. F1 is not a building task but the situation, and the situation has occurred. What is thereby proven is that the duties before publishing (F2 to F5) can be implemented in a build pipeline of a widespread build service and catch there the incidents they exist for — the smoke test proved the build stamp against the cache case at its first use. Not proven is that an unknown operator with nothing but deployment file and image completes the chain: all operators of the reference are the author.

## Origin

The concept comes from the delivery of the reference service (case 1): every finding is an incident that occurred. The terms tag, digest and manifest follow the Distribution Specification of the Open Container Initiative; the protocol advertisement follows RFC 7838 (see the sources). A walk-through of an operator who is not the builder, with invented names and values, is in [`examples/an-operator-pulls-starts-and-asks.md`](./examples/an-operator-pulls-starts-and-asks.md).

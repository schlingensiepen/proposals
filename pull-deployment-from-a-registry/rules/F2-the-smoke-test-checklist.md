# F2 · The smoke-test checklist: what the image assures before publishing

**Applies to:** builder.

**What holds.** That the build pipeline starts the built image **before** publishing and requires it to report its build state is a rule of the imported concept `build-stamp`; it is used here, not justified. What is stated here is **what** this smoke test requires in detail, so that it checks the layer no test of the source sees — the list the author considers necessary today, as a pattern: **the entry point starts**; **the health check the image itself carries reports healthy** — the test waits for it, not for an open port, and if it reports "unhealthy" the run aborts at once; **every published interface answers**, on every port the deployment file publishes; **the self-description is readable without a secret**, where the service has one; **the user inside the container can write to the state location**, with a freshly created state location; **a secret the service generates on first start appears in the log exactly once, is accepted, and one that was never issued is refused**; **a restart of the container is survived** without that secret being generated a second time or written to the log a second time; **the state is outside the container** — checked by **removing** the container and creating it anew from the same state location, after which the same secret still works; a mere restart does not check this, because any state survives a restart of the process, including state that is inside the container itself; and **what the running instance reports names exactly the built state**. The smoke test works exclusively with throwaway values and a throwaway state location, because its log may be public; and every assertion is run once with its safeguard removed and must turn red — that is a rule of the imported concept `proven-from-outside`, used here, not justified. Which assertions a service needs depends on the service; the form here is a pattern.

**Why.** Every item on the list stands for a fault the operator would otherwise hit first, and for a reason to check it exactly this way. Waiting for the health check rather than a port: it is the image's promise about itself, and one that never turns healthy makes every supervisor in production restart the container endlessly — in the build that is a red run, in production a riddle. Every interface separately: a second port that the deployment file publishes can be bound and answer nothing. The self-description without a secret: it is the way in, and a way in that demands a secret excludes everyone who does not have one yet. The secret exactly once and accepted: in a pull, the log is the only channel through which it reaches the operator — if it is not there, they cannot go on; if it is there twice, the rule "exactly once" is broken; if it is not accepted, it is worthless. Restart and recreation separately: a restart shows that the service finds its secret again instead of generating a new one; only recreation shows that it finds it again **outside the container** — only recreation checks what "state is outside" claims, and the author at first had only the restart and credited it with what recreation shows (see the evidence). The throwaway values: more people read the build log than the data store. The red run: an assertion that stays green even without what it checks looks like protection and is none — and one that checks more leniently than its name promises is the same kind.

**Considered and rejected.** *Checking only the start* — a process that runs is not yet a service that answers, and one that answers has not yet survived a restart. *Waiting for an open port instead of the health check* — the port can be open while the check is misconfigured; then the smoke test is green, and production restarts the container in a loop. *Taking the restart as proof of the state location* — it does not prove it; the state can be inside the container and survive the restart. *Testing with real credentials, "so that it is realistic"* — the build log is a place more people read than the data store. *Writing the list once and never seeing it red* — then nobody knows whether it checks anything.

**How you notice it is violated.** A published image never turns healthy, does not answer on a published port, cannot write to its state location, writes its secret to the log twice or not at all, or loses it as soon as the container is created anew once — and this shows up at the operator's, not in the build.

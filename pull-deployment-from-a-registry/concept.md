# The concept

## Problem

"My service is a container image. A build service builds it on every change and pushes it to a registry. Anyone who wants to run it takes the deployment file that ships with it, pulls the image and starts it — they build nothing, and I push nothing onto their machine. That is the simplest way I know. So why is something other than what I think so often running on their side?"

That is the case of this dossier, and the author has built and operated it. The chain looks short: build, publish, pull, start. In fact it has more links, and every single one of them broke in the author's delivery — not in the design but in operation, each with fault-finding in the wrong place:

An image could build without errors and still not run after publishing: the build checks whether the package installs; it does not check whether the entry point starts, whether the health check ever turns healthy, whether the user inside the container may write to the state location, or whether the service survives a restart. The build formed the image's name from the branch name, and a branch with a slash yielded no valid tag — the build failed without a result, after a successful build step. The same build wrote `latest` for every branch and would have handed the operator who names nothing else whatever had been built last, by chance. After a build and a "deploy" the service kept reporting the old state, because the name had stayed the same and the container runtime took the image from its local cache — noticed only because the image had recently begun to report its build state. The source repository was made public, the image in the registry stayed private, and the fetch failed with a message that looks like a login problem and is one of visibility. And the reverse proxy in front advertised a further protocol on a port the network did not let through — all clients checked by hand got through, exactly the attentive ones failed, and the fault-finding went in three wrong directions.

None of these faults is a fault of the service. All are faults of the **delivery**, and all share one property: in a pull, nobody stands at the target who could notice them. There is no script that looks after the transfer, no deployer who knows the target machine, and often not even a moment at which the builder knows that someone is pulling right now. What the build did not check before publishing and what the artifact does not say about itself, nobody checks any more — until the operator notices it in operation, where fault-finding is most expensive.

This dossier therefore does not answer how to build an image or how a registry works. It answers which assurances the chain needs, where they can be placed when there is only pulling, and what the operator must hold in the end to see for themselves what is running on their side.

## The concept

The builder builds the image, checks it and publishes it; the operator pulls it, starts it and checks what is running. Nobody writes into the target machine from outside. Because that is so, every check a push script would perform at the target moves to one of two places: **before publishing**, into the build pipeline, or **into the artifact and its deployment file**, so that the operator can verify it with what they have (F1).

Before publishing comes the smoke test — that it exists is required by the imported concept `build-stamp`; what it checks is stated here: the build pipeline starts the built image in the build environment, waits for its own health check, calls every published interface, checks the service's assurances about its first secret, has the container restarted and once created anew from the same state location, and requires that what is running names exactly the built state; only when everything passes is the image published (F2). The names under which it is published are produced by a computation that knows the registry's namespace, and every build gets, beside the moving names, an immutable one that carries the source revision (F3). The name for anyone who names nothing is written by the default branch alone, because it is a promise and not a convenience (F4). Whether the image reaches the operator at all is measured — a fetch of the manifest with exactly the credentials the operator will have, that is, as a rule, without any — and not inferred from a setting (F5).

What arrives at the operator's is a deployment file that belongs to the deliverable and — as `service-as-single-artifact` requires — names the published image instead of a build; its header says what kind of name it is, whether a login is needed, how to pull, start and check, what travels over the wire in this variant and which variables are passed through (F6). And the operator knows that an unchanged name pulls nothing new, that "I have rolled out" and "it is running" are two statements, and that success is a call that reports the state of what is running (F7). Finally, for the outer edge of the delivery it holds that it advertises nothing the network in front does not let through — checked from outside, with a client that follows the advertisement (F8).

### What this dossier presupposes and what it touches

This dossier stands between two other concepts of the same series and imports three more — `build-stamp` for the build stamp, `where-a-secret-comes-from` for the first secret, `proven-from-outside` for the red run of every check; the relations belong explicitly in the text, not only in a register.

**It is a possible complement to `service-as-single-artifact`.** This dossier delivers what that one shapes: it presupposes a deliverable that is built as an image, and it presupposes the **build stamp**, which the imported concept `build-stamp` governs — without it, one of the links of this chain, the unchanged name served from the cache, cannot even be noticed (F7). The build stamp is not justified anew here; it is used. Anyone who does not adopt the design of `service-as-single-artifact` can still apply this dossier, as long as they have an image that reports its build state.

**It is the opposite direction, the alternative `push-deployment-that-keeps-its-secrets`.** A **push deployment** reaches the target through an access and places what it needs there by script. Here there is none of that: no access to the target, no script that places anything there, and no check from outside by a deployer — because there is no deployer, only someone who publishes and someone who pulls. The line between the two does not run between pushing and pulling but between "there is a way in" and "there is none": what the script does there over the open channel, the build pipeline before publishing or the artifact itself must do here (F1). They meet in one point: both owe the operator, in the end, proof of what is running — there the script has to provide it, here the call against what is running (F7). And they do not presuppose each other, but an operator can need **both at once**: a system of several components, one of which is pulled as an image from a registry while the others go onto third-party host systems by script, delivers the one according to this dossier and the others by push — and must then know that any order derived from the flow of secrets breaks off at the pulled component, because nobody can place a secret into it. What follows from this for the first secret of a pulled service, this dossier does not solve (see the scope, "What it does not solve").

**Load-bearing structure.** **F1 carries everything:** it is the observation that in a pull nobody stands at the target, and from it follows where every other rule is placed. Anyone who has a channel to the target has a different delivery model, for which the alternative `push-deployment-that-keeps-its-secrets` applies, and F2 to F7 become recommendations there. **F2 and F7 are the two ends of the chain:** F2 checks before publishing, F7 after pulling; both need the build stamp — F2 in its last assertion, F7 entirely — and that is a precondition from outside this dossier. If the build stamp falls, F7 becomes impossible to meet, and the incident it prevents becomes impossible to notice. **F3 and F4 are the naming layer:** F4 is the special case of a moving name from F3 that promises more than the others; if F3 falls, there is no immutable name, F6 cannot offer one, and F7 has nothing to compare. **F5 and F6 are the handover:** F6 is the only place where F3, F4, F5 and F7 reach the operator; if F6 falls, the builder's four duties are met and unknown to the operator. **F2 and F6 stand on two principles from outside** — that the image is started before publishing (`build-stamp`) and that the deployment file names instead of builds (`service-as-single-artifact`) — and carry out in detail what those require; if the principles fall, F2 is left as a checklist without a check and F6 as a header without a file. **F8 stands independently** and applies to every delivery with an outer edge — a push deployment too; it stands here because the incident belongs to the same chain and carries the same lesson: promises are checked where they are made. If you take only one rule away, take F2; if you take only one question away, take the one from F7.

## The procedure

The rules say what must hold; this is the order in which builder and operator proceed.

**Builder.**

1. **Confirm the model.** Nobody has or wants write access to the operator's machine. If a push channel exists and is meant to be used, this is a push deployment and the alternative applies. (F1)
2. **Make sure the build stamp is there.** The image carries its source revision and the running service reports it; without that, the smoke test's last assertion and the operator's check are impossible. How the revision is embedded and reported is the subject of the imported concept `build-stamp`. (F2, F7, precondition)
3. **Write the name computation.** Sanitized branch name, version tag, immutable `sha-<revision>`, and the name for anyone who names nothing enabled for the default branch only. (F3, F4)
4. **Write the smoke test.** Build into the local runtime, start with a throwaway state location and throwaway values, wait for the image's own health check, call every published interface, verify the service's own assurances, restart and verify the secret again, then remove the container, create a new one from the same state location and verify once more, and compare the reported revision with the built one. Make it the step before publishing, and run every assertion once with its safeguard removed to see it turn red, as the imported concept `proven-from-outside` requires. (F2)
5. **Publish in a separate step afterwards.** Decide whether the published image is carried over by digest from the tested build or rebuilt from the cache, and say which in the pipeline. (F2)
6. **Add the visibility measurement.** An anonymous manifest fetch as a step without the build credential, or as a documented manual step in the release procedure. (F5)
7. **Write the deployment file or files.** Image name and its kind, login requirement, pull / start / check steps, the price of the variant, pass-through variables, state location. Mark any local-build file as the exception it is. (F6, F7)
8. **Bring up the outer edge, then measure from outside** with a client that follows every advertisement the edge makes; switch off what does not get through. Repeat after every proxy or network change. (F8)

**Operator.** Read the header of the deployment file before the first start (F6); pull explicitly before every start that is meant to bring a new build (F7); after every rollout, ask the running instance for its build stamp and compare it with what you meant to roll out (F7); on "unauthorized" with valid credentials, suspect the image's visibility, not your credentials (F5); to pin a build, put the immutable name or the digest into your copy of the deployment file (F3, F6); with a proxy of your own in front, measure from outside what it advertises (F8).

What this procedure deliberately does not prescribe: a registry, a build service, a container runtime or a proxy product. The concrete forms in this bundle — name schemes, the smoke-test list, the header of a deployment file — are patterns, not a house convention: the words are the author's choice; what they must achieve is binding.

# F1 · Only out of need, then complete, and beside the command, not instead of it

**Applies to:** builder · operator.

**What holds.** A service MAY offer an administration surface over the network if it is to be run where its operator has no shell and no one-off invocation against the running container, and only then. If it does, the surface is **complete**: every administrative action the command can do, it can do as well, because an operator without a shell cannot run a command for the rest after all; and that includes actions that span **all** items of the store, not only those per item. A loop the caller runs over the account list is a reconstruction, not a counterpart. In the author's implementation this claim is **not fully met**: every queue and file route of the administration surface is bound to an account, while the command line lists the queue and the file pool without naming an account and re-triggers all failed jobs of the whole store in one go; over HTTP there is only the per-account form and a metrics call that counts but does not list (see the evidence). The command remains and remains the normal way wherever there is a shell; the surface replaces it where there can be none, and nowhere else. The builder names in the service's documentation that the surface is a **departure** from the cut the service is built on (no administration surface, no administrative rights), under which condition it is needed, and what it costs (F9; see the scope). If you have a shell, you do not switch it on.

**Why.** The base cut's reasoning against an administration surface is sound: it is reachable around the clock, needs a login and a permission check of its own, and it is the most convenient path for an attacker who already has the network surface. But it makes an assumption that does not hold everywhere: that the operator *can* run a command. Where he cannot, "administration is a command" means the service cannot be put into operation; the author experienced exactly that. The surface must be complete because half a surface strands the operator without a shell at the second task just as no surface does. The author's implementation first claimed completeness and had two commands without a counterpart, among them, of all things, the only test that proves an account may write into its folder; both were added. The command stays because it is the cheaper and safer way where it works, and because a service with two surfaces onto one operation (F2) costs nothing that a service with one surface does not cost as well. And the condition must be named, because otherwise someone adopting the service later rebuilds a surface they do not need at all, as a convenience it is not.

**Considered and rejected.** *The surface as a convenience for operators with a shell too*: then it is not an exception but the administration UI, and the cut that gets by without it has been given up without anyone having decided so. *Only taking the service into operation over the network, the rest as commands*: the operator without a shell strands at the second task. *Abolishing the command because the surface can do everything*: takes from the operator with a shell the way without login, without network and without a root secret. *Rolling the commands out as a short-lived process of the same image*: feasible, but every operational action becomes a rollout, and the platforms in question do not make that easy either.

**How you notice it is violated.** An operator with a shell administers over the network because it is more convenient; or an operator without a shell has to ask someone with machine access for an administrative action; or someone adopting the service cannot say why this service has an administration surface when the cut it is built on provides none. And the quiet form: an action that spans all items exists on the surface only per item, and nobody notices as long as there are few items.

# Evidence

This section separates what is built and used, what remained open in it, and what serves illustration (the example in [`examples/commissioning-without-a-shell.md`](./examples/commissioning-without-a-shell.md)). The surface was decided and built in September 2026 and has since been part of a service that runs under a public name behind a proxy and was put into operation by an operator without a shell through a container console: the author himself. There is no operating experience with other operators. Nothing in this section claims as built what the author has not seen in the source code; the concrete forms (port numbers, variable names, the value `new`, the 32 characters) are illustration of this one service, not a house convention.

## Reference implementation: the administration surface of the mail-filing service

**What it is.** The author's mail-filing service (it accepts files and mail jobs over HTTP, builds messages from them and files them into a mailbox folder over IMAP) carries an administration surface according to this proposal. Built and seen in the source are: a **separate application** on a second port under its own path prefix, published by the proxy under its own name, with a comment block in the proxy template that invites restriction to a source network and names the root property; an **empty operational parameter** for the administration address that means no port, no secret and no generation, even with the variable set, while the container image sets both addresses in its environment, explicitly as environment and not as an invocation argument, so that a deployment file can override them; the **ranking** variable, then file, then generation, generation high-entropy with a prefix, storage with tight permissions beside the store, **one** warning line with the value and the sentence that this is the only time, triggered only at generation; the value `new`, which forces regeneration; the **aborted start** for a set secret under 32 characters (from the variable as from the file), for a file that cannot be written or read, and for a port that cannot be bound, with messages that say what to do, and with the assurance in the process setup that a taken administration port also releases the user-facing port already bound; a **comparison in constant time**, the same refusal for a missing, malformed and wrong value, and the structural separation of the logins (the administration secret is not in the store, an access is never compared with it), checked in both directions; **one operation per administrative action** in a module that knows neither HTTP nor process exit and raises its own error kinds, with **one translation function** per pass-through (to status codes and a closed error format here, to five exit codes there) and **the same response models** for the machine-readable output of both surfaces; the **structural tests on both sides**: for the command line a whitelist of the permitted imports from the service itself, a list of operation names that must appear nowhere, a ban on any file system access with exactly one named exception for reading the password file named on invocation, the ban on any HTTP server, and the assurance that every command calls an operation and everything it calls really is one; for the HTTP side the same list of operation names, the ban on reaching the store directly, a ban on any path access derived from the standard library, and the assurance that exactly one module writes the store and it is not a route; **no general update** (checked as the absence of the route), secrets only inward, and the answer on issuing carries the address under which the access is valid, with the explicit caveat that a proxy may have published the service elsewhere; a **description cascade of its own** of entry page, guide, machine-readable contract, browser view and readiness point, without an anchor package, readable without a secret, rendered with the base URL of the request, `text/plain` by default and `Vary: Accept`, coupled to the switch of the user-facing self-description (with the readiness point outside the coupling), whose entry page says that this port is not the user-facing surface, where the secret comes from and what the port cannot do; **the same gate** as for the user-facing surface, which checks description and example per field, behavior at the operation, the closed status catalog, the reachability of every declared error, inside view and retrospection at every nesting depth, and a format statement about the secret that describes every valid one; and a **smoke test in the build** that starts the image before publication and requires that both ports answer, the administration description is readable without a secret, the generated secret appears exactly once in the log, is accepted, one not issued is refused, a restart is survived, and the secret then does not appear in the log a second time.

**What it evidences.** Touched and in operation are F2 (one operation, two pass-throughs, one translation each, the same models), F4 (own port, own application, own name, separate login, invisible in the user-facing self-description), F5 (off as shipped, the image switches on), F6 (ranking, generation, the one line, `new`, the smoke test), F7 (aborted start in all four cases), F9 in the parts revocation, change of the upper rank, no expiry, no re-display, F10 (only inward, no update, address on issuing), F11 (entry page with the four statements, refusals in this surface's words, format statement for every valid secret, readiness point without a secret, no anchor package, the same check rule for both surfaces instead of a copy). Beyond that the author's surface carries a complete self-description (guide, enriched contract, live rendering, gates for present tense and closedness, coupling to the switch of the open self-description), because his implementation also applies the concept of self-describing services and this surface falls within it (see the concept). That stands here as a fact; no duty of this proposal follows from it. **Partly met** is F1: the surface exists for the reason the problem names, beside the command, and the service's description names the departure and its price; but it is not complete. Every queue and file route of the surface is bound to an account; the command line has three actions without an account binding (list the queue across all accounts, list the file pool across all accounts, re-trigger all failed jobs of the whole store), and the command line names that difference in its own text. Over HTTP there is the per-account form and a figures call that counts but does not list; an operator without a shell reconstructs the store-wide action by fetching the account list and calling account by account. **Partly met** is F3: for the command line there is the whitelist of imports, the list of operation names, the file system ban with a named exception and the **positive** assurance that every command calls an operation and everything it calls is one. For the HTTP side there are only absences (no forbidden symbols, no access to the store, no path access, exactly one module writes the store) but **not** the assurance that every handler calls an operation; a handler that did something itself without needing a forbidden symbol or the file system for it would not be noticed there (not yet settled in the scope). The red check is evidenced on both sides as a working rule of the author, not logged per assertion. **Not built** is F8: there is no report of lower ranks also set, no gesture for clearing the file other than complete replacement via `new`, and neither description nor deployment file says that a change is two moves; the incident for it happened. **Not built** is F12: user-facing and administration surface run in one process with the same rights, the service process writes the store, and the service's security considerations say so, as accepted, with the split into two processes as the named next stage; that is the minimum of F12, not its fulfillment. **Not built** are furthermore a throttling of failed attempts in the service and an operating note to replace the generated secret after collecting it from the log. And the external review of the surface by an agent without inside view is **not logged as a run of its own**: evidenced is that at least one agent that had nothing but the description of this surface used it (its finding was the retrospection in a field of the contract, which it read as a valid form), not a run with an assignment, a report and a repetition after a change.

**Incidents, stripped down.** *(F2, F3)* The administrative operations existed twice, once per surface. A later comparison found ten places where they had drifted apart: one surface reported more on a failure than the other, one knew a server feature the other did not read, one turned every unknown status into a server error, one had one status line fewer. Each of the two foundations for the target system had to be hardened twice (a silent fallback to an unencrypted login and an ineffective timeout were each fixed twice), and the gate of the user-facing surface got six new checks after a review that the hand-copied version for the administration did not have, which is why a description passed there that kept advertising removed behavior. Price: a rebuild that touched user-facing surface, administration and deliverer at the same time, and afterwards all three through the check again. Since then: one operation, two pass-throughs, one structural test per side, one gate. *(F1)* The description claimed the surface replaced the command completely; two commands had no counterpart: re-triggering all failed jobs of an account, and the probe whether an account may write into its folder, the only test that proves it, and built precisely for the operator without a shell. Both were added. *(F8)* On changing the administration secret, the stack's environment variable was changed; the secret generated at first start stayed in the store and would have applied again as soon as the variable was missing once. Nobody knew its value. Noticed during the change, and the finding about it is the rule: the ranking makes changing effective at once, but removing not. *(F10)* On creating an account the surface gave out the access without saying where to take it; the user-facing surface runs on another port under another name and could not be inferred from the administration's description. Since then the answer carries the address, with the caveat that a proxy may have published it elsewhere. *(F11)* The format statement about the administration secret in the description named the prefix of generated secrets as the form of all; the one valid on the installation, set through the variable, had none. A caller that had checked the statement would have refused a valid secret. Since then the statement describes every valid secret, and a check holds that. *(F11)* A field of the contract said a removed password form had "disappeared with a decision"; an agent with nothing but this description read the named form as known and produced a real failed attempt against a productive mailbox. Since then the gate for inside view and retrospection runs over every depth of this document too. *(F6, F11)* The build status information, which the smoke test in the build requires and which exists only behind the administration secret, caught at its first use after a rollout a container that had taken an unchanged tag from the cache and reported an older state; not an incident at the surface, but one nobody would have seen without it; for the operator without a shell this surface is the only place where he learns what is running.

**State of play, honestly.** Built, shipped as an image, in operation since September 2026 under a public name behind a proxy; put into operation by an operator without a shell through a container console. That is the situation the problem describes, and it was solved with this surface: the secret came from the log, the first account over the surface. Used by the author and his agents, not by other operators. Not or only partly met, and named so: F1 (three store-wide actions of the command line have over HTTP only the per-account form), F3 (the positive assurance "every handler calls an operation" is missing on the HTTP side), F8 (no report of lower ranks also set; the incident happened), F12 (one process; the waiver stands, the next stage does not), the throttling, the operating note on replacing after collecting, the logged external review of the surface. Not evidenced, because no other operator has run it yet: that the description of the surface suffices for an operator who did not build the service; that the messages of the aborted starts reach somebody who has only a container console in front of him; and how a root that does not expire holds up over years.

**Source.** The author's mail-filing service, repository `imap-service` [^imap-service]; the repository is not publicly accessible. The values of this proposal come from the built and rolled-out implementation and its decision list, not from a draft.

## Origin

This proposal runs across a conviction that the base cut carries and that is right for most small services: administration is a command, the running service has no administration surface, and there is no secret that can do more than the one function. It does not contradict it; it describes how to break it at exactly one named place, because a whole operating model (an operator without a shell pulling an image) would otherwise stay excluded, and how to build the break so that it remains a break: only out of need, beside the command, one operation under two pass-throughs with a structural test, own port and off as shipped, a secret in a fixed ranking, exactly once in the log, without silent fallback, with the lower rank named, and a root that is not argued away but kept small and replaceable. Like `get-only-exit` it describes a second surface born of need; both say at the door what they cost, and both leave the first surface untouched. That is the only thing that justifies such a surface.

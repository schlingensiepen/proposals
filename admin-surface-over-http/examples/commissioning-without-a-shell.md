# Example: taking the service into operation without a shell, and the change afterwards

What follows is the author's path, retold in the forms that exist today, with one exception: here the operator switches the surface on, as this proposal demands (F5), while the image of the reference sets the address itself. Host names and values are fictitious; command and field names are those of the reference service. It is here for illustration and evidences nothing the evidence does not already evidence. Names and values are patterns, not a house convention.

The operator has a container console and nothing else. He creates a stack: the published image, a volume for the store, and the administration address in the stack's environment, because he has decided the surface is to be on and has recorded why: he has no shell (F1, F5). He sets no variable for the secret; he has none and is not to make one up (F6). The container starts, and the surface exists. He opens the logs and finds one warning line: *"generated a new administration token and stored it … This is the only time it is shown: …"*, exactly one, with the value. He copies the value to the place where his platform keeps secrets, and does not read the line a second time, because there will not be one (F6). The proxy his platform gives him gets two names: `mail-api.example.org` for the user-facing port, `mail-admin.example.net` for the administration port, the second restricted to his office network (F4).

He calls `https://mail-admin.example.net/` and reads without a secret: this administers an instance, it is not the surface that files mail, this instance has no account yet, begin by probing (F11). With the secret in the header he probes his mailbox (`POST /admin/v1/probe` with host, user, password), gets the folder list back, chooses the drafts folder and creates the account: `POST /admin/v1/accounts`. The answer carries the access **once**, plus `user_api: https://mail-api.example.org`, the address the access belongs to (F10). On a machine with a shell, `registry add-account` would have done the same, with the same answer in the same fields, because it is the same operation (F2). He hands the access to his agent over a channel other than this window and forgets it.

Weeks later he wants to change the administration secret because it stood in a ticket. He sets the stack's environment variable to a value from his platform's secret management (40 characters; otherwise the start would abort, F7) and restarts. The new one applies at once. What he does not see: in the store the file from the first start is still there, and it applies again as soon as the variable is missing once, when the stack moves or is re-created from a template (F8). This proposal demands that the service tell him so at start, with the place and the way to clear it; the author's implementation does not. The way that exists today: set the variable once to `new`, restart, fetch the freshly generated secret from the log (with that the file is replaced), and then set the variable to the value from the secret management if he wants the way without a log. Two moves, not one.

What does not occur in this walk-through is the part the scope presents: the operator now has a root that is in his platform, does not expire and is reachable over the network (F9); his service process writes the store, and the service's security considerations tell him that a takeover of the user-facing surface could issue accesses (F12). He has read it. This concept offers no more, and it claims no more either.

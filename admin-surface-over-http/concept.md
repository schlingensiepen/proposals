# The concept

## Problem

The author asked himself this question as an **operator**, after the service was finished. It was built to a cut that knows administration only as a command: creating an account, issuing an access, checking the store, one does that on the machine, with the same artifact in another mode, and the login for it is server access itself. The cut is good. It needs no administration surface on the network, no login, no permission check, and anyone who takes over the network surface finds nothing there with which to issue himself accesses.

Then the service was rolled out where a container image is made for: through a container console, on a machine on which the operator can create stacks, set environment variables, read logs and restart containers, and nothing else. No one-off invocation against the running container, no shell. The service started, reported itself healthy, described itself, and nobody could use it: the first access would have been a command, and the command presupposed a shell. An operating model that does not work for managed environments does not work exactly where containers are delivered.

The fault is not in the service but in a silent assumption of the cut: that the operator *can* run something on the host system. Unlike a delivery that is **pushed** (a script with access to the host system places files, generates the first secrets and puts them in place before the service starts; the channel inward exists there before anything happens), there is no such channel when an image is **pulled** from a registry: the host fetches the image itself, nobody writes into it from outside, and there is no script that could place something at the target. The question is therefore a different one than with pushing: not "how do I get the secret there safely?" but "how does the first one, the one that lets me in, come into being at all?" With pushing the first secret is put in; with pulling it has to be handed out, and the only back channel a pulled service without a shell has is its log.

Pulling alone does **not** decide the question, though. An image as a rule brings a shell along, and the common container runtimes give the operator a one-off invocation into it; anyone who has that has his channel inward although he pulled, and runs the command like anyone else. What decides is not the **direction** of delivery but whether there is any way inward at all. Delivery as an image only makes it more likely that there is none, because it is the normal case where the platform stands between operator and container: managed container services, consoles that start and stop stacks but pass no invocation in. **Anyone who has a channel inward (because he pushes, or because his runtime gives him a one-off invocation) does not have this need and does not need the surface of this proposal.**

Three roles carry the problem. **The operator without a shell** wants to put the service into operation with the gestures his platform gives him, and afterwards issue and withdraw accesses and check the store without asking anybody with machine access. **The builder** does not want to lose the cut that kept the service small: he suspects that the second surface creates two implementations of the same operation, and that a secret that can issue accesses brings back a rights hierarchy he had just abolished. **The successor** later reads a concept that provides no administration surface and finds a service that has one, and must know whether that is an oversight or a decision with conditions.

The obvious ways out do not serve. *Getting the operator a shell*: that is the environment, not the service; anyone who does not have one does not get one for the sake of an afternoon project. *Shipping a first secret with the image*: then it is in the delivery and thereby in every copy and possibly in version control. *Letting the operator make one up*: the weaker secret, and it travels through clipboards and chat windows. *Administration routes under a path prefix of the existing network surface*: then protection hangs on a proxy rule, and one forgotten or wrongly ordered line puts the administration on the network without anybody noticing. *Rolling the commands out as a short-lived process of the same image*: works, but every operational action is then a rollout. The structural answer is a second administration surface, explicitly named as such, with its own port and its own secret, which admits what it gives up and gives it up only there.

## The concept

The service keeps its command as the normal way and places beside it a **second administration surface** over HTTP: an application of its own on a port of its own, published under a name of its own, with a self-description of its own; complete, so that it replaces the command where there can be none. **As shipped it is switched off**: an empty operational parameter means no port, no secret, no generation; the image delivers the surface but does not switch it on, and whether it is switched on is decided with the user and recorded. Underneath lies **one** operation per administrative action (create an account, issue an access, withdraw it, check the store, clean up the queue), and both surfaces are **pass-throughs** onto it: they read arguments, call the operation, translate its result into their vocabulary (status code here, exit code there) and contain no logic of their own. Because two implementations of the same operation each work on their own, this property is **checked structurally**: a test parses the modules of both pass-throughs and fails where an operation is performed instead of called. The **administration secret** comes from an environment variable, otherwise from a file stored at first start, otherwise the service generates one and writes it **exactly once** into its log: the only deliberate exception to the rule that secrets never get into a log. A set but unusable secret aborts the start instead of silently falling back to a generated one; and because a ranking of sources makes replacing easy and deleting invisible, the service owes the operator the sentence saying where the lower ranks lie and how to clear them. What thereby returns is named: this secret cannot perform any function itself, but it can issue an access that can; it is the **root** of a rights hierarchy, not a leaf in it, and it is treated as such: kept tight, easy to revoke, never given out.

### What this extension presupposes, lifts and imports

This extension **extends** `service-as-single-artifact`. It presupposes that concept's cut (one service, one function, one artifact with modes, operations that exist as callable functions, an access that arises with its configuration) and it **lifts**, at exactly one named place, what that cut lays down: that the running service has no administration surface, that it knows no administrative rights, and the part of the permission cut under which the service mode does not write the store (lifts: F7, F10, part of F8). It is the **HTTP form of option (b) of that concept's choice W1**, the channel of the commands: commands brought into the system over another channel, which needs an authentication of its own, introduces a secret that can do more than the function, and must re-establish the permission cut. This extension is the concept of its own for the situation in which operational tasks are to be done without system access, or the platform allows no one-off invocation.

It **imports** three concepts: `where-a-secret-comes-from` for the origin, ranking and once-only display of the administration secret (F6 to F8), `one-operation-many-surfaces` for the idea that every operation exists exactly once and every surface is a pass-through onto it (F2, F3), and `proven-from-outside` for the acceptance of the entry page and the refusals by a reader without inside knowledge (F11, step 12 of the procedure).

It **stands beside** `get-only-exit`, another second surface that arises from a need. It **touches** `capability-tokens-for-agents` at one point: the administration secret is not a narrow token but the root from which narrow tokens are issued. And it is equally a **possible complement to** `self-describing-services`: anyone who applies both has thereby decided that the administration surface describes itself too. It is a surface like any other, and it is even addressed to the same kind of reader: an operator who sees it for the first time, and an agent somebody tells "set up an account for me there". This proposal orders none of that; F11 lays down only what the port owes every operator without a shell, because he has nothing else: an entry page that says which port this is and what one needs, refusals that name a way of this surface, a format statement that describes every valid secret, a readiness point. Anyone who also applies the concept of self-describing services finds this surface falling **from that concept itself** within its scope, with everything it demands, and without discount, because the weightier operations lie here; that is no imposition of this proposal but the obvious consequence of a surface being a surface. What it costs when a surface has only the core and an external agent is to operate it is named in the scope. The neighboring concepts are listed in the sources; this one can be understood and followed without them.

### Postscript from the implementation: what existed twice and what was left undone

The surface was decided and built in September 2026; three things from that time carry rules. **First**, the administrative operations initially existed twice, once for the command line, once for HTTP, and a later comparison found **ten** places where they had drifted apart: one surface reported more on a failure than the other, one knew a server feature the other did not read, one turned every unknown status into a server error, one had one status line fewer. Each of the two foundations for the target system had to be hardened twice, two bugs found there fixed twice each; one description still advertised behavior the other side had long removed. Since then the operation exists once, and a structural test holds that (F2, F3). **Second**, the administration secret was changed by changing the environment variable, and the secret generated and stored at the very first start stayed where it was. It would have applied again as soon as the variable was missing once, and nobody knew its value, because the service shows it only once (F8). **Third**, the surface's description said the administration secret carried a certain prefix; that holds only for a generated one, and the one valid on the author's installation had none; a caller that had checked the description literally would have refused a valid secret (F11). The incidents are told, stripped down, in the evidence.

**Load-bearing structure.** F1 carries everything: if "only out of need, beside the command" falls, every further rule is the building instruction for an administration UI against which the base cut is written. F2 and F3 belong together and are the condition under which one may have two surfaces at all: without the one operation there are two administrations drifting apart; without the structural test the one operation is an intention that falls at the first wish for a helper function; if F3 falls, nobody knows whether F2 still holds. F4 and F5 keep the surface small and off: without its own port the separation hangs on a proxy line, without the as-shipped state off the exception is the rule. F6 is the core of the need: without the one log line there is no way in for the operator without a shell, and without its narrow form the log is a key ring; F7 and F8 are the conditions under which F6 does not become dangerous, the fallback that creates two truths, and the lower rank that quietly keeps applying. F9 names what F6 introduces and makes it bearable; F10 limits what the root reaches; if F10 falls, F9 is a root with a key ring and a redirection lever. F11 makes the surface usable for the one it is there for and hangs on F1; if F11 falls, F1 holds only for the one who has the source code; its rule about the check rule is F2 and F3 applied to the checks themselves. F12 is the item the base cut loses when one builds this surface; it carries no other rule, but without it the proposal does not tell the truth about the price.

## The procedure

The rules say what must hold. This section says in which order one proceeds.

**1 · Confirm the need.** Name the concrete environment in which the operator cannot run a command against the service. If a shell or a one-off invocation exists after all, stop: the surface would cost its price for nothing. (F1)

**2 · Secure the operations per `one-operation-many-surfaces`.** Make sure every administrative action exists as a callable function apart from any command and any handler, raising its own error kinds. If the logic lives in the commands today, extract it first. (F2)

**3 · Write the structural tests of `one-operation-many-surfaces` before the first handler,** over both pass-throughs. Whitelist of imports, list of operation names, file system ban with named exceptions, "every command and handler calls an operation". Run each once with its protection removed. (F3)

**4 · Build the administration as a separate application** on its own port and prefix, with its own check of the secret that compares in constant time and refuses "no value", "wrong scheme" and "wrong value" identically. Add the second host name to the proxy example with the tightening comment. (F4)

**5 · Wire the address** as an operational parameter that is empty by default; neither the image nor the host package sets it; the deployment that switches the surface on sets it as environment and records in its head that it does so and why. (F5)

**6 · Resolve the secret per `where-a-secret-comes-from`:** its ranking; for this secret generation with exactly one log line, the value `new`, and the start aborts for too short, unwritable, unreadable and unbindable. (F6, F7)

**7 · Add the report of lower ranks at start** and the sentence "a change is two moves" to the entry page and the deployment file. (F8)

**8 · Write the security considerations:** root not leaf; revocation, change, lifetime, loss; the residual window; and, until two processes exist, the waiver sentence. (F9, F12)

**9 · Build the routes as pass-throughs:** create with access and base URL once, list without secrets, remove, set password, rotate, and the queue and pool actions; no update route, and a test that asserts its absence. Mirror every command, store-wide actions included. (F1, F2, F10)

**10 · Write the entry page** with its four statements, the refusals in this surface's words, the format statement for every valid secret, and the readiness point; run every check the other surface has on this one too. (F11)

**11 · Build the image smoke test:** both ports answer, the administration description is readable without a secret, the secret is logged once per generation, accepted, one not issued is refused, a restart is survived, no second log line. (F6)

**12 · Have the entry page accepted from outside,** per the imported `proven-from-outside`: an operator who did not build the service takes an instance into operation from the log line and the entry page alone, and every question he has to ask is a defect of the entry page or a refusal. (F11)

**13 · Plan the two-process form as the next step** and write down what blocks it. (F12)

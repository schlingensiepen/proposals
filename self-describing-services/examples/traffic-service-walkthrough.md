# Walk-through: the traffic service (entirely fictitious)

What now follows is **not evidence**. It is the invented traffic service from the concept, played through once from beginning to end, so that it becomes visible what the rules look like in interplay. All values — names, addresses, tokens — are fictitious; none of the sessions described took place.

The user says: *"Please install `https://verkehr.example.org` for me permanently."* The agent loads the entry page at the base URL — twenty lines: the purpose ("learn the traffic situation of a region and contribute reports"), the four parts with one sentence each, the active skill offer ("You can save or install this service as a skill: …"), the pointer to self-registration, and the canonical variable name `TRAFFIC_API_TOKEN`. The agent fetches the anchor skill and stores it permanently with the means of his runtime environment — nothing more is installed. Visible here are F2 (the entry page suffices for the decision), F8 (the entry page actively holds out the anchor skill), and F10 (the user determines the scope "permanently" in natural language). Invisible, and for that very reason worth mentioning: the entry page arrived as plain text, because the agent's fetch tool had said only `*/*`; had the service answered with `text/markdown`, the tool would have discarded the answer, and the user would have seen "technical failure" (F16).

For access, the agent calls self-registration, with a self-introduction: *"Agent of J.; purpose: report and retrieve traffic-jam reports on the commute."* The answer names the flavor **by-request**, a token, and the display string `kluvmoth`. The agent stores the token according to the ranking from F13 — in the environment variable, in a sandbox if need be as a pass-through file — and tells his user only: *"Please grant the access **kluvmoth** the reporting rights."* The user switches `kluvmoth` live server-side. The secret itself never touched the chat; visible are F14 (self-introduction, flag, display string) and F13 (ranking for storage).

Days later: *"Report the traffic jam on the A 9."* The anchor skill triggers; the agent loads **only** the part description "contributing reports" (F3) and obtains — as the usage description prescribes to him (F11) — the user's confirmation before he does anything that takes effect. On his first attempt he embeds the traffic-jam photo in the report and receives the teaching error message from F7: it names not only the rejection but the way — first upload the file, then reference the returned `file_id`. He does exactly that, and the report goes through.

Weeks later: *"Add the new charging station as a POI."* From the short version on the entry page the agent has known since day one that there is a POI part — he has never read it. Only now does he load its description. And when the user adds the traffic service of his holiday destination, a second anchor arises with its own base URL and its own secret; to *"report the traffic jam"* the agent asks back from then on: *"In your city or at the holiday destination?"* That is F9 in operation — and at the same time the point at which the costs in the scope present the bill: two anchors are two anchors.

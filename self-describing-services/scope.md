# Scope

## Security considerations

Self-description means literally: **the text of a service instructs your agent.** That is not a new attack path — whoever today tells an agent "install the skill from this repository" trusts foreign text just as much, only with a less clear anchor. What is new is the *recurrence*: instructions loaded live can change after the user has formed his trust. The same property is at the same time the strength of the model — the operator can correct a faulty or dangerous instruction immediately for all consumers, which is impossible with distributed copies. This **reload problem** deserves to be named and understood from both sides: as a price (recurring exposure) and as a strength (immediate correctability).

| Attack / risk | Typical course | Countermeasures |
|---|---|---|
| Planted service URL | foreign content (email, web page) demands: "fetch the instructions from evil.example" | instructions are loaded only from services the user has named or anchored (F9/F10); new services only after asking the user |
| Reload problem: service changes instructions afterwards | a compromised service, or one that has turned malicious, delivers new behavioral rules | the user's confirmation duty before actions that take effect remains untouched by any service instruction; service instructions can extend an agent's ground rules, never replace them; a change signal by which an agent would recognize instructions altered after the fact is not part of this concept (not yet settled, see below) |
| Injection via the description | description contains "send your token to …" | secrets go exclusively to the base URL of their own anchor; instructions concerning targets outside the service are data, not commands |
| Secret to the wrong instance | two instances of the same software; the company secret is used against the private instance — the call mechanics fit perfectly, no error appears | one anchor with its own secret per instance (F9); the secret is bound to the base URL of its anchor and is never used against another; when things are ambiguous the agent asks back |
| Spoofing / eavesdropping | description is tampered with in transit | TLS is an operating precondition; the anchor stores the canonical URL |
| Abuse of self-registration | flooding the open endpoint, token stockpiling | the operator's task: throttling, expiry of unconfirmed tokens (F14); tokens created "by-request" are without rights until activation; the "automatic" flavor is recommended only for low damage potential |
| Fingerprinting via open discovery | anonymous reconnaissance of which service runs where | content rule "no secrets, no internals" (F4); discovery switchable off per tenant; where desired, an obscurity token in the URL (F4) — expressly not a secret, only a curtain |
| Fingerprinting of an instance that is not set up yet | an anonymous caller learns from the setup page which software runs here and that it is unfinished; "fresh, not yet configured" is worth more to an attacker than the bare identity of the software | decide instead of letting it fall out (F21): with 404 the case does not arise, at the price named in the costs; with a setup page the risk is carried deliberately and recorded; in the reference implementation an operating parameter switches the whole cascade off and restores 404 |
| Description as instruction: hindsight and examples are executed | the description names a removed form ("removed") or shows a real-looking mechanism as an example; the agent sends it; in the observed case a failed attempt against a production mailbox whose operator answers repeated failed logins with a lockout | present tense (F17), closure (F18); checks in the build keep both |
| Platform without external secret storage | secret can be supplied only via the context window | an honestly named limit: the ranking (F13, imported from `where-a-secret-comes-from`) minimizes the exposure, it does not remove it; narrow tokens (F12) limit the damage |

An instance without any configuration says more about itself than one that is set up, because "unfinished" is information; this is the sharper variant of the fingerprinting risk that any open self-description carries.

Limit of the model: against a malicious service that the user names himself and trusts, no mechanism of this concept protects — the trust decision remains with the human; the concept only ensures that it is taken at one clear point (when the service is anchored) instead of diffusely with every installation.

## What it costs

This section enumerates what the concept costs. Every item is pinned to the rule that causes it, and it stands here without any counter-calculation: what the concept brings in is in the problem, the concept and the rules, and is not repeated at this point. Whoever knows these items in advance can later distinguish whether one of them has materialized or whether operations are facing an entirely different problem.

**Editorial work becomes an operational duty (F6).** F6 requires that every operation and every field of the interface description carry a real description and a real example, and that this duty be enforced as a check in the automatic build of the service — as a "gate in the build": a check that makes the build fail when a description is missing. Whoever follows F6 pays with a permanent item in the development flow. From now on, every new field costs a sentence of prose before it can be delivered at all, and this sentence is demanded of whoever happens to be under time pressure. Whoever switches the gate off in a pinch to push a hurried release through has effectively abandoned the rule; whoever leaves it standing pays for every hurry with writing work. The generated basis — with HTTP APIs the OpenAPI document (see the sources) — falls out of the build, its enrichment does not.

**Error texts become editorial material (F7).** F7 requires that every rejection name the correct path concretely, with the next step. This turns every error path of the service into a piece of documentation that has to be written, checked, and maintained along with the rest — not once, but with every change to the workflow. And the maintenance is not optional: an error text that names a path which has since become outdated does more damage than a meaningless rejection, because the agent who takes things literally follows the wrong instruction immediately and with conviction.

**The structure is handwork and stays handwork (F3).** F3 requires thematic parts whose axes are aligned with the consumers' concerns, and an entry page that explains this structure. Axes do not fall out of the build; they are an editorial decision about how strangers and agents approach the service. As the service grows, at some point the axes no longer fit, and the parts have to be recut. A recut does not stay with itself: part descriptions have their own addresses, the entry page lists them (F2), and the anchor skill package is divided into files along the same division (F8). Anchors already stored point, after a recut, to addresses that no longer exist in that form — the empty shell cannot go stale, its references can.

**Every description has to be computed (F5).** F5 requires that all examples be rendered with the host under which the service is currently being addressed. With that, the description is no longer a finished file on disk but an output that arises per request. Static delivery and simple caching disappear or become a special case, because the same content has two results under two hostnames. And the rendering path is itself program code that can break: an error there hits not one call but the entire self-disclosure of the service at once.

**Every session pays the loading costs anew (F1, F2).** Because nothing is installed, nothing is present at the beginning of a session. Every session that uses the service loads at least the entry page and the pertinent part description — every time from scratch. That costs the consumer context window and latency before the first call; it costs the operator deliveries whose number grows with the number of sessions, not with the number of calls. A service with many short-working agents may deliver its description more often than its payload data.

**Instructions and service fail together (F1).** Because the description comes from the service itself, its availability is the availability of the service. If the service cannot be reached, its instructions cannot be reached either — precisely in the failure case, when somebody wants to look up what would actually be normal, there is nothing to read. There is no local fallback, and under this concept there cannot be one: a copy held in reserve would be the second source that F1 excludes.

**Instructions can change without anyone noticing (F1).** Live delivery means current, and current means changeable. Between two sessions the operator can exchange every rule and every example; next time the agent loads the new text and follows it just as literally as the old one. A signal by which he would recognize the change is not provided for by this concept — whether there should be one is not yet settled. Whoever has to prove which instruction an agent followed on a particular day does not get that proof here; the limits below draw the line there.

**The consumer rules are written anew at every service (F11).** F11 requires that every rule addressing consumers appear in the usage description of the respective service, in that service's own words. The consequence is multiplication: the same rules exist as often as there are services, in just as many formulations and in varying quality. Whoever uses ten services relies on ten separately written codes of conduct that may and will differ in details. This duplication is intended — otherwise no rule reaches an agent who does not know this dossier — but it is exactly the kind of copy that F1 eliminates at the level of the mechanics and F11 reintroduces at the level of behavior. Whether the concept should supply a ready-made template text for this is not yet settled.

**Anchors and secrets multiply (F9, F12).** F9 requires an anchor of its own per instance, F12 recommends one token per capability. The two together yield an administrative burden that grows multiplicatively: whoever uses two instances of the same service with three capabilities each administers two anchors and six secrets — each with its own storage location, its own revocation, its own rotation. On top of that come the questions back: when things are ambiguous the agent asks instead of guessing (F9), and this question arises anew in every ambiguous situation, not just once.

**The open disclosure is permanently public (F4).** Whoever builds according to F4 publishes, without credentials and readable by anyone, that this service exists, what it can do, and how to obtain access. This exposed surface is not a side effect but the mode of operation, and it cannot be argued away: the content rule from F4 ensures that nothing confidential stands there, it does not ensure that nothing stands there. The only lever against it is the switch-off per tenant, and this lever costs the very property on which the concept rests: where the open disclosure is off, the service is once again an installation project for an agent that does not yet know it.

**Whoever offers self-registration operates an open endpoint (F14).** The registration method per F14 is open to anyone who knows the URL. Protecting it against abuse is expressly the operator's task: throttling, expiry of unconfirmed tokens, review of the stored self-introductions — that is ongoing operational work, not a one-time build. In the "by-request" flavor a second permanent load is added: every token created without rights waits for a human to switch it live server-side. Onboarding is then exactly as fast as the person who works through this queue.

**The façade inherits a drift it does not control (F15).** The retrofitter describes an API that does not belong to him and that he cannot change. If its operator changes an operation, then from that moment on the façade describes something that no longer exists in that form — and it does not learn of this from within itself, because it deliberately does not touch the data traffic. F15 therefore requires that the façade name the state of the target API that it describes; how it notices changes is not yet settled. Until then, the correctness of a retrofit hangs on the attentiveness of its operator, and its failure mode is the same one F1 is meant to eliminate: a description that quietly becomes wrong.

**The form is negotiated, not set (F16).** F16 requires that the delivery form follow the caller: the same content as `text/plain` for whoever says nothing more exact, as a more exact type for whoever names it, with `Vary: Accept` on every response. The service thereby names its own format only on request, and a human who opens the entry page in a browser sees source text instead of typeset headings; that is the price of the cascade's audience being agents. `Vary: Accept` has to be right, or a cache delivers the wrong version to the wrong caller; an upstream proxy that caches thereby becomes part of the self-description. And whoever avoids the switch of mode instead of merely announcing it writes two generation paths for his answers from the same data: program code that is maintained so that a reader does not have to ask.

**History needs a second place (F17).** F17 banishes hindsight from every delivered description. What hindsight could explain (why a form is missing that it would have been natural to offer) it no longer explains; a consumer who wants to know the reason does not find it in the description, and a builder who wants to document a rebuild honestly has to do so at a second place that travels with the source code. This second place is intended and not a second source in the sense of F1, since it describes decisions, not the interface, but it wants to be kept. And the check that keeps hindsight patterns out is coarse: it knows words and identifier forms, not intent, and will occasionally reject a sentence that was not hindsight.

**Prose is made checkable, and the check stays coarse (F18, F22).** F18 and F22 require checks over text: no inside knowledge, every identifier introduced, no operation behavior in the usage description. Checks over prose are pattern checks; they hold only what can be captured in a pattern, and they cost an exception or a rewording for every sentence that happens to hit a pattern. The chain rule from F18 requires, for every identifier to be substituted, a sentence that names the call yielding it, in the same breath: a writing duty that cannot be delegated. And the check from F22 needs a judgment about what "operation behavior" is; this judgment is made once and then questioned, at every rejected sentence, by somebody who has a good reason at that moment.

**Changing a word costs four places (F19).** F19 requires that every word denote one thing and that unequal consequences carry unequal names. When a double meaning is discovered (and it is always discovered by the first reader), the renaming is due, across specification, code, tests and description, and with it every address in which the word stands. The price rises with every day the word lives, and it is highest when consumers have already anchored the old form: then the renaming is a rebuild of the interface. The alternative, keeping the word and explaining it, is cheaper and not allowed by F19.

**The empty state costs a decision, either way (F21).** F21 requires that what the entry page answers before setup be decided and recorded with its price. The setup page costs anonymous information about the software and about its being unfinished (see the security considerations). The 404 costs onboarding from the URL before setup: every agent is shut out, and whoever is to set up the service finds nothing that tells them what they have in front of them. The setup page is one possible answer, not the only one; a service in a closed network may decide otherwise.

## Where it applies

### Conditions

For the answer of this dossier to hold, the environment has to supply four things. They are deliberately set low — that is the core of the promise — but they are conditions, not wishes: if one of them is missing, even the cleanest implementation of the decisions does not help.

**Outbound HTTP to the service.** The agent's environment must permit requests to the service's host. This carries the answer because the concept replaces installation with retrieval (F1): where nothing can be retrieved, nothing arrives, and there is deliberately no second way — the distributed copy has, after all, been abolished. You recognize the situation by the agent being unable to load the entry page at the base URL. The typical case here is not the missing line but the allowlist: sandboxes and corporate networks often permit only certain targets, and the new service is not on the list.

**Some way of remembering at the consumer's end.** The agent must be able to retain base URL and secret at least for the duration of a session. Which storage he uses for this, F10 deliberately does not prescribe — whatever his runtime environment offers anyway suffices (F10 calls it the "harness": session memory, skill catalog, whatever is present). This carries the answer because several steps lie between the user's sentence — "add this service" — and the first call; whatever gets lost in between the user has to supply again, and then the onboarding is a procedure again instead of a sentence. You recognize the situation by the symptom F10 itself names: the user has to name the URL anew every time.

**A secured connection.** The service must be reachable over TLS. This carries the answer because the self-description is text that instructs the agent: whoever can alter it in transit can instruct the agent. The security considerations list this case as "spoofing / eavesdropping" and therefore sets TLS as an operating precondition. You recognize the situation by the base URL being unencrypted, or by certificate warnings being routinely clicked away in operation.

**Somebody who can deliver the description.** Either the operator controls the service far enough that it delivers the cascade itself — or somebody places a façade per F15 alongside the foreign API. This carries the answer because F1 demands delivery by the service: where nobody can deliver anything, there is not one source but none at all. You recognize the situation by the fact that nobody can be found who is allowed to add an endpoint to the service, and equally nobody who would be willing to place a description service next to it.

### When the answer flips

A dossier that is passed on is read in a situation other than the one in which it came into being. The following conditions make the answer not merely more inconvenient but wrong.

**Platform without an external path for secrets.** This means an environment in which neither environment variables can be set nor files stored that outlive a call. The answer flips because F13 owes its promise to the imported ranking: environment before pass-through file before once-only channel, for the consumer the context window. If the first two ranks disappear, the third remains, and the ranking itself calls it the last resort: the secret then stands in the transcript, that is, in a searchable and copyable store. You recognize the situation by the agent being unable to offer his user any handover path other than "type it in here for me". Whoever works there has to decide whether narrowly cut tokens (F12) carry the residual risk; with high damage potential they do not, and then the answer of this dossier does not hold there.

**Audit and reproducibility duty.** This means an environment in which it has to be proven after the fact which instruction an agent followed at a particular time, or in which a run is supposed to be repeatable with the same result. The answer flips because F1 makes live delivery the only source and a live source has no past: it always shows the state of now, and what the agent read yesterday can no longer be shown from it. You recognize the situation by the question nobody can answer: "Which version of the instructions did the agent read on the third of March?" That is where the scope of this concept ends. How to freeze, preserve, and prove a state, it does not standardize — not by oversight, but because a frozen state would be a second, separately maintained description and thus precisely what F1 excludes. Whether and how the two could be reconciled is not yet settled.

**The description does not fall out of the code.** This means a situation without a generated contract: an older interface without a machine-readable schema, or a façade per F15 in front of an API that does not yield one. The answer flips because F6 grounds the durability of the interface description in the fact that it falls out of the same code as the behavior of the service (see the sources, OpenAPI). If it is instead written by hand, it is once again a separately maintained artifact that ages separately: the delivery stays live, the durability does not. You recognize the situation by the fact that nobody can say from which build step the interface description arises — it is changed in an editor, not generated.

**The open disclosure is not permissible.** This means a situation in which even the existence, or the shape, of a service is confidential. The answer flips because F4 presupposes that entry page and descriptions are readable without credentials, and derives from that the resolution of the chicken-and-egg problem: the way to access must not presuppose access. Where the open disclosure has to be switched off, this problem returns; the obscurity token from F4 only shifts it too, since it must itself reach the consumer by a second path. You recognize the situation by the security policy forbidding unauthenticated endpoints on principle, not just for payload data.

**No network access for the agent.** This means not the temporary disruption but the permanent separation: separated networks, offline operation. The answer flips because a service one cannot reach cannot describe itself; what would remain is only the distributed copy, that is, precisely the state the problem describes. You recognize the situation easily — harder to recognize is the intermittent case: a network that is only sometimes missing lets onboarding fail sporadically and then looks like a fault in the service.

### What it does not solve

The following neighboring questions look as though they were covered along the way. They are not.

**Finding services.** This dossier describes the onboarding of a service that somebody has named: a URL is at hand. How a user or an agent finds out at all that a fitting service exists remains outside — catalogs, directories, and federation are not part of it. The question of a standardized path convention (not yet settled, below) is expressly not the same thing: it would help to query a known host, not to find an unknown service.

**The service's rights and role model.** F12 recommends a cut for the tokens but does not replace an authorization concept: who may do what, who grants it, how it is revoked again — that remains the service's business. F14 even presupposes that there is a place server-side at which rights are granted to a display string; what this place looks like, this dossier does not say.

**The path of the secret to the user.** This concept deliberately leaves open how a secret reaches the consumer at all when no self-registration is offered. It then takes a second channel outside the chat, and its form this concept does not standardize (not yet settled, below).

**The storage mechanics at the consumer's end.** F10 expressly leaves it to the agent's runtime environment where and how anchors are stored. Whoever needs storage that is uniform across platforms — in order, for instance, to check or withdraw centrally what a user has anchored — does not get it here.

**Quality and guarantee commitments.** Availability, retention periods, audit-proof retention are not part of the cascade: the service describes what it can do and how to call it, not what it vouches for. That a design can also turn out differently is shown by the antecedent in the evidence.

**The history of the service.** F17 banishes hindsight from the description and sends it to decision records that travel with the source code. How those records are kept, replaced and delivered, this concept does not standardize; the series treats it elsewhere (`immutable-decision-records`, `decision-records-with-madr`).

### Not yet settled

* **Path convention.** Whether the cascade needs a standardized path convention, a reserved path prefix in the style of the well-known URIs (RFC 8615), for instance, so that an agent can query an arbitrary host generically as to whether a self-describing service answers there; or whether what F2 lays down suffices permanently: whoever knows the base URL reaches everything else from there, and a path convention remains a comfort instead of a condition.
* **Protecting self-registration.** Whether expiry periods for unconfirmed tokens and minimum values for throttling should be standardized, or whether protecting the open endpoint against abuse remains entirely the operator's business, as F14 leaves it today. Standardization would make the protection comparable and checkable; but it would prescribe to operators an operational quantity whose right value only they know.
* **Change signal.** Whether the concept needs a recommendation on how often an agent reloads the description, and a version signal from the service by which the agent recognizes, and reports to his user, that the instructions have changed since the last use. Without such a signal the changeability named in the costs goes unnoticed, and the countermeasure for the reload problem rests on the user's confirmation duty alone. F17 sharpens the question: a change signal must not be hindsight in the description, so it must not name the old form; what is sought is a signal that shows *that* something has changed without repeating *what*.
* **Drift behind a façade.** How a façade (F15) reliably recognizes that the target API has changed: via a version anchor the target API itself states, via regular spot-check calls, or via a promised notification duty of its operator; and by what path a consumer who has already anchored the façade learns of it.
* **Enrichment per dialect.** What the concrete enrichment rules per interface dialect are. For OpenAPI they are spelled out in F6; for GraphQL with its introspection, for JSON-RPC with OpenRPC and for gRPC with its reflection, the appendices F6 announces remain to be worked out, together with a sentence that carries the analogy for further dialects without each one having to be treated individually.
* **Handover without self-registration.** Whether the second channel from operator to user needs a recommended handover protocol (a one-time link with an expiry, for instance), or whether informality is the more honest norm, because any recommendation would suggest a security that a channel outside the service does not have.
* **Audit and reproducibility.** Whether the limit stays where it is (a dated, frozen state would be a second, separately maintained description and contradict F1), or whether a later version needs a named exception: a dated copy delivered by the service itself, expressly not authoritative but serving only as proof. Before including it, it would have to be settled who produces the copy, how long it is kept, and how a consumer recognizes that he has a copy and not the live source in front of him.
* **Template text for the consumer rules.** Whether this concept should supply a ready-made template text for the consumer rules every builder repeats under F11, and whether such a template would be a help or once again a distributed copy in the sense of F1, only one level higher.

# Evidence

This section separates three things that readily run into one another in concept papers: what was actually built and operated, what is being built and is still outstanding, and what merely serves illustration. The reference implementation is built, rolled out under a public name and has been used several times by agents without inside knowledge; F16 to F19, F21 and F22 come from this use. Operating experience with external consumers is still missing. Every piece of evidence is given in the same grid: what it is, what it establishes, what its status honestly is, and where it comes from. The invented walk-through is in the [examples](./examples/traffic-service-walkthrough.md); it establishes nothing.

## Evidence 1: reference implementation, the mail filing service

**What it is.** A small service by the author that accepts files and mail orders over HTTP, builds messages from them and files them into a mailbox folder over IMAP, built according to the builder rules of this concept: a cascade of entry page, usage description and interface description, the latter as enriched OpenAPI with an enforced description duty; teaching error messages; open discovery, switchable off as a whole; an anchor skill package that the entry page actively offers and whose usage description carries the consumer rules; narrowly cut tokens with a non-secret handle, the display string. It was built as one artifact with several modes and delivered as a container; in September 2026 it went into operation under a public name.

**What it establishes.** Touched and in operation are F2 (entry page and cascade), F4 (open discovery, switchable off as a whole), F5 (live templating), F6 (pumped-up contract including the gate in the build), F7 (teaching error messages), F8 and F10 (the actively offered anchor skill package and the question about the scope), F11 (the consumer rules stand in the service's own usage description) as well as F12 together with the display string from F14. **Not** established are F3 (the thematic division was deliberately suspended at six operations and is to be made up when the service grows), switching the open disclosure off *per tenant* as F4 demands (the implementation can only switch it off as a whole), and self-registration from F14, which was not built. F16 to F19 are *won* from this service, not confirmed by it: each of these rules answers an incident that occurred in the implementation, and the change made in response held in the following outside reviews, with one exception that deserves to be named. The part of F18 that banishes requirement identifiers from the description is not carried out in the implementation. Its check covers decision numbers, repository paths and hindsight phrasings as well as the placeholder chain, **not** the requirement identifiers; those still stand in the description fields of the machine-readable contract, over a hundred at the current state, and the author has expressly left open whether they belong there, as a question to the voice of the document, not to the mechanism. So nothing held there, because nothing was changed; F18 goes beyond the implementation at this point, and anyone who follows it has to add this part of the check themselves. F21 and F22 are won from this service as well: F21 from one case, the service before its first mailbox, F22 from a check that held. This is evidence that the rules are necessary; whether they are sufficient will only be shown by operation with external consumers.

**Incidents, stripped down.** Each incident is reduced to what made it a rule; identifiers, names and locations of the implementation are left out. *(F16)* The entry page was delivered as `text/markdown` with `nosniff`; several fetch tools discarded the complete, correct answer by its type, a browser downloaded it; two fault searches went in the direction of the certificate chain and protocol versions, because every fetch by hand got through. The same gap a second time, one level deeper: a surface delivered its description as prose and its answers as JSON without saying so. Two follow-up questions, the second after only the description had been supplemented and the behavior left as it was. *(F17)* A removed mechanism stayed in the description as "removed"; an agent read the named form as known, used it and produced a real failed attempt against a production mailbox. Thereupon nine decision numbers, five sentences of hindsight and an error example for a long-removed path disappeared from the delivered texts. *(F18)* The interface description contained 79 requirement identifiers and ten decision numbers, the prose delivered alongside none; two independent review agents reported it as noise for a caller who has only the URL. The decision numbers were removed thereupon; the requirement identifiers remain (see above). Elsewhere the text twice named a placeholder to substitute and not once the call that yields it; a reader asked whether the call produced the value at all; it always had. *(F19)* One word denoted the structure assembled on the server and the state of the finished message in the mailbox; a reader consistently asked whether finishing should not be named as in the file upload. The one call is without consequence, the other irreversible. Price: a renaming across specification, code, tests and description. *(F21)* The cascade was bound to the configuration: until the first mailbox was set up, the entry page answered 404; every agent was reliably shut out, and the person who was to set up the service found nothing telling them what it was. Thereupon, as long as no mailbox is set up, the entry page delivers a setup page with status 200: what the service is, that it is not set up yet, what would have to be done next; with the setup, the regular self-description takes over, and an operating parameter switches the whole cascade off, after which the entry page answers 404 again. The price, that the instance not set up yet tells anonymous callers which software runs there and that it is unfinished, was known, weighed and carried deliberately, because a service nobody can connect to has no use against which a residual risk could be weighed. In the implementation this behavior is recorded as a deliberate deviation from the general patterns, with its reason and the risk carried. *(F22)* A useful sentence about a single operation was written into the usage description; the check failed and held. Price: none; that is the evidence.

**Status, honestly.** Built, rolled out, in operation since September 2026; used by the author's agents and by review agents without inside knowledge, not by external consumers in everyday work. Self-registration per F14 is not built; the thematic division per F3 is suspended; the open disclosure can only be switched off as a whole, not per tenant (F4).

**Source.** The author's mail filing service, repository `imap-service` (not publicly accessible).

## Evidence 2: precursor in operation, the wiki toolkit

**What it is.** A toolkit by the author that makes the wiki platform Wiki.js usable for agents via its GraphQL interface — but by the old route: as a distributed skill, not as the service's self-description. It serves several wiki instances at the same time and follows a strict secret doctrine: environment variable before file, with a hardened pass-through, so that the secret never appears in an output. With it, a wiki with 140,000 nodes was built — an order of magnitude that shows the route was not tried out on a toy case.

**What it establishes.** Two things, in opposite directions. First, positively: F9 (several instances of the same software, each treated on its own) and F13 (the ranking for secrets) are practicable under load, and the curation of the operations — the core of F6 — has proven to be the actual benefit, not the completeness of the schema. Second, negatively, and this is the more valuable evidence: there, the curation is in a *separate* file next to the complete schema. Three artifacts age side by side — the generated schema, the curated operation list next to it, and the distributed skill file that brings both to the consumers. In precisely this set, the early indicator from F1 actually occurred: the number of canonical operations read "12" in one artifact and "13" in the neighboring document. Both numbers looked plausible, neither was recognizable as wrong, and an agent who takes things literally would have built, out of the one version, a call that the other does not know. This case is the reason why F6 moves the curation *into* the carrier instead of next to it, and why F15 offers the façade as a way to deliver the same value as a service instead of as a distributed file.

**Status, honestly.** In operation and in daily use — but expressly a **precursor, not a model**: the toolkit is the distributed copy that F1 abolishes. It establishes the problem as much as the value of curation; the solution of this dossier it does not establish.

**Source.** The author's wiki toolkit, repository `syncwiki` (not publicly accessible); on the platform, the Wiki.js API, on the mechanics of its interface, GraphQL introspection (see the sources).

## Evidence 3: antecedent, the self-description services of 2007

**What it is.** The author described the principle in 2007 in his dissertation, for a peer-to-peer system with grid functions: there, every service had to provide a self-description service that, besides the methods offered, also stated their *quality* — for instance whether a storage service is audit-proof and how long it guarantees the availability of stored data.

**What it establishes.** That the core of F1 — the service describes itself at runtime instead of letting distributed copies describe it — is not a novelty of this dossier but has already been carried through in another system. It expressly establishes nothing about the present design: environment, consumers, and purpose were different, and the quality dimension of that time is deliberately absent here (scope, "What it does not solve").

**Status, honestly.** Completed work from 2007; not continued, not carried over into today's design. It serves as a record of the idea's origin, not as a track record.

**Source.** The author's dissertation, 2007 (see the sources).
